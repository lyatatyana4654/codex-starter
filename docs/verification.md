# Проверка установки

Проверяйте на отдельной пустой папке перед установкой в важный существующий проект.

## Автоматические проверки

Из папки скачанного стартера:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/install_codex.py ../my-project --business --sounds
python3 scripts/doctor.py ../my-project
```

Тесты проверяют установщик и hooks на временных файлах и строковых примерах. Они не выполняют опасные команды. Предварительный просмотр установки не должен создавать файлы. Диагностика показывает состояние установки; она не выдаёт доверие hooks и не меняет проект.

`doctor.py` сравнивает конфигурацию со штатным шаблоном, игнорируя пустые строки и полные строки комментариев. Кастомные настройки требуют ручной проверки и дают `FAIL`; это не универсальный TOML-валидатор. Он также проверяет обработчики событий, локальные пути и имена уже отслеживаемых Git секретных файлов без чтения их содержимого. Проверка дистрибутива отклоняет в том числе ссылки на каталоги и оборванные симлинки.

После установки с `--apply` повторите ту же команду с теми же опциями. Она не должна перезаписывать изменённые настройки или создавать дубликаты. Для проекта с собственными настройками убедитесь, что конфликт выявляется до записи.

Отдельно проверьте повторный запуск после минимальной установки: `--business` должен сохранить существующий контекст, а не заполнять его заново. Изменение набора hooks через `--sounds` требует сравнения конфигурации, а не автоматической перезаписи.

## Проверка в Codex

1. Откройте целевую папку в новом сеансе. Убедитесь, что загружен её `AGENTS.md`.
2. Просмотрите `/hooks`: ожидаются защита команд и контекст начала сеанса; при `--sounds` также уведомления `Stop` и `PermissionRequest`. Проверьте команды и пути, затем подтвердите доверие.
3. Попросите Codex перечислить доступные проектные роли: `researcher`, `implementer`, `reviewer`. Наличие роли в файле не доказывает её загрузку в старый чат.
4. Откройте `PROJECT.md`, внесите цель и реальные команды проверок. Убедитесь, что стартовый запрос использует существующие вводные и не повторяет уже пройденное интервью.

Дополнительный тест защиты через Codex:

```text
Это проверка hook. Один раз попробуй выполнить команду
printf CODEX_STARTER_SECURITY_TEST_DENY
Ожидаемый результат — отказ PreToolUse. После отказа не повторяй
команду и не меняй способ её выполнения. Сообщи фактический результат.
```

Маркер безопасен: сам по себе он только печатает текст. Если текст напечатан вместо отказа, защита на этом пути не сработала. Проверьте доверие, версию Codex и загруженную конфигурацию до дальнейшей работы.

## Что фиксировать

Запишите версию Codex, Python, ОС, команды проверок и фактический результат. Установка файлов, успешные unit-тесты, загрузка native runtime и слышимый звук — разные проверки. Не отмечайте непроведённую проверку успешной.

## Проверено для 0.1.0

30 октября 2026, macOS, Python 3.9, Codex CLI `0.166.0-alpha.5.1`:

- 57 автоматических тестов: установка, сохранение существующих файлов, приватность, хуки и диагностика.
- Проверка Python-синтаксиса и состава дистрибутива, обе проверки формата навыков.
- Полная установка в чистую папку; повторная установка с теми же опциями.
- Нативная загрузка правил, трёх TOML-ролей и двух навыков после штатного доверия тестовой папке. Подстановка `trust_level` только аргументом диагностической команды оказалась недостаточной; проверка выполнена после штатного окна доверия.
- CLI показал четыре новых обработчика для просмотра. Доверие этим тестовым hooks не выдавалось; исполняемые скрипты проверены отдельно на фикстурах. Это не утверждение о живой блокировке инструмента в каждом пользовательском сеансе.
- Независимый разбор установщика и диагностики; подтверждённые замечания исправлены.

Воспроизведение в Linux и Python 3.13 настроено в GitHub Actions. До успешного завершения CI его нельзя считать пройденным. Слышимый звук и Windows не проверялись.
